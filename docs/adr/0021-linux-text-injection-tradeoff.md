# ADR 0021: Linux の `InputKind::Text` はクリップボード貼り付け方式を当面維持する

**状態**: 承認 (2026-08)

## コンテキスト

`crates/miru-input/src/platform/linux.rs` の `inject_text()` は、テキストを
クリップボードへ書き込み Ctrl+V を合成することで文字入力を実現している。
2026-08 の First Principles 監査(FEATURE_AUDIT 項目18)で以下の欠陥が判明した:

1. **ユーザーのクリップボード内容を毎回破壊する**(データ損失)
2. **`xclip` 依存のため X11 限定**。ファイル冒頭は "Works on both X11 and
   Wayland" と書いていたが、キー/ポインタ注入(uinput = カーネルレベル)には
   当てはまってもクリップボード経路には当てはまらない**誤記**だった
3. **Ctrl+V が貼り付けでない環境で機能しない**。大半の端末エミュレータは
   Ctrl+Shift+V であり、`InputKind::Text` の主な利用者である MCP エージェント
   (`type_text` ツール)は端末へ打鍵する場面が多いため、これは主用途での破綻
4. クリップボード書き込み失敗時に `Ok(())` を返しており、**何も入力されて
   いないのに成功として報告**していた

自然な代替案は「キー合成方式」— 文字を物理キー+Shift の組に分解し uinput へ
直接注入する(本ブランチで追加した `miru-input/src/keymap.rs` を再利用できる)。
これなら 1〜3 がすべて解消する。

## 判断

**キー合成方式へは切り替えない。クリップボード貼り付け方式を維持する。**
ただし上記 4(サイレント失敗)と誤記(2 のドキュメント部分)は即時修正する。

## 理由

### uinput は原理的にキーボードレイアウトを知り得ない

uinput はカーネルレベルの仮想デバイスであり、送出するのは**物理キーコード**
だけである。それを文字へ解釈するのは上位のコンポジタ/X サーバで、注入側から
現在のレイアウトを問い合わせる手段がない。

これは理論上の懸念ではなく、uinput 自動化ツールの事実上の標準である
**ydotool が抱える既知・未解決の制限**として文書化されている。ydotool は
設定されたレイアウトに関わらず US QWERTY として打鍵するため、Dvorak 環境で
`This is a test` と打つと `Ydco co a y.oyv` になる(ReimuNotMoe/ydotool #43、
Plasma 6.2 でのレイアウト無視 #254)。ydotool の README も
「世界中のレイアウト数を知る術がないため生キーコードを使う」と明言している。

### つまりトレードオフであって改善ではない

| 方式 | クリップボード | レイアウト正当性 | Wayland | 端末 |
|------|----------------|------------------|---------|------|
| 現行(貼り付け) | **破壊する** | **全レイアウトで正しい** | 不可(xclip) | 不可 |
| キー合成 | 安全 | **非US配列で誤入力** | 可 | 可 |

どちらも他方を包含しない。キー合成へ切り替えると、
「X11 の GUI アプリで非US配列を使っているユーザー」にとっては
**現在正しく動いているものが誤入力になる退行**である。

### 「貼り付け直前に保存し直後に復元する」案も採らない

クリップボードを退避→設定→Ctrl+V→復元すれば 1 だけは解消できるが、
貼り付けは**非同期**である。対象アプリがキーイベントを処理してクリップボードを
読むより先に復元すると、**古い内容が貼り付けられる** — クリップボード消失より
悪い「リモートアプリへの誤テキスト挿入」を招く。適切な待ち時間は環境依存で、
本変更を書いた環境ではコンパイルもテストも不可能(crates.io / rustup が
ネットワーク遮断)なため、タイミング依存の競合を盲目的に導入しない。

### 将来の正しい解

方式の二者択一ではなく、**表示サーバごとに正しい手段を使う**のが本筋:

- **Wayland**: `zwp_virtual_keyboard_v1` で**自前のキーマップをアップロード**
  できるため、レイアウト非依存に任意の Unicode を入力できる(`wtype` の方式)。
  これは制限のない真の解。項目4(PipeWire/Wayland 対応)と同時に実装するのが自然
- **X11**: XKB に問い合わせて目的の文字を生成する keycode+修飾の組を解決する
  (`xdotool type` の方式。レイアウトに無い文字は未使用 keycode を一時的に
  再マップする)
- どちらも使えない場合のみ、現行の貼り付け方式へフォールバック

## 影響

- 現行の貼り付け方式を維持(退行リスクを回避)。
- **即時修正した点**: `inject_text()` はクリップボード書き込み失敗を
  `Ok(())` で握り潰さず伝播するようにした。ファイル冒頭の
  「X11/Wayland 両対応」の誤記を、キー/ポインタ注入のみが両対応であり
  クリップボードと `Text` は X11 限定である旨に訂正した。
- **未解決として残る点**(FEATURE_AUDIT 項目18 に記録): クリップボード破壊、
  X11 限定、端末で不動作。これらは上記「将来の正しい解」で解消する。
- 本 ADR は方式変更を**禁止するものではない**。テスト可能な環境で
  Wayland virtual-keyboard / X11 XKB 経路を実装する際に置き換えること。
  盲目的な US 配列決め打ちへの単純置換だけを退けている。
