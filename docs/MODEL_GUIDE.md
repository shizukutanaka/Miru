# Miru 実装モデル使い分けガイド(私専用)

作成: 2026-07。このガイドは一般論ではなく、`claude/sweet-franklin-l5a1yw`
ブランチでの実セッション(2026-06〜07、Sonnet 5 / Fable 5 混在で作業)の
結果から逆算した、**Miru の残作業に特化した**推奨です。根拠は各項目に
このセッションでの具体例を付記しています。関連: `docs/roadmap.md` セクション0
(優先順位)・セクション0.5(市販レベル品質ロードマップ)、`docs/FEATURE_AUDIT.md`。

## 前提: このセッションで何が起きたか

- 修正19件・4新機能(TOFUゲート等)をコミットしたが、**サンドボックスが
  crates.io への通信を拒否**し `cargo check`/`cargo test` が一度も実行できなかった。
  すべて「定義元との手動突き合わせ」でのみ検証。この制約は今後も起こりうる
  前提として扱うこと。
- 調査エージェント(Explore)は有用だったが**誤検知が1件確認された**(handshake の
  agent token 未統合という指摘は実際は正しい設計だった)。裏取りせず鵜呑みに
  しない運用が必要。
- `deep-research` skill は2回試行し2回とも「週次検索枠切れ」で失敗。Web検索前提の
  調査には現状使えない。
- TypeScript側は `npx tsc -b --noEmit` で実際にコンパイル検証できた(Rust と違い
  npm レジストリは許可されている)。この非対称性を利用し、フロントエンド変更は
  必ず tsc で検証してからコミットする運用が既に機能している。

## モデル使い分け表

| タスク種別 | 推奨モデル | 理由(本セッションの実例) |
|-----------|-----------|--------------------------|
| grep/Read だけで完結する棚卸し(パス実在確認、i18n キー同期チェック、CI設定の有無確認) | **Haiku** | 判断を要さない機械的検証。本セッションの `docs/FEATURE_AUDIT.md` 全パスの実在確認、ja/en 106キー完全一致の確認はこの粒度 |
| 定義済みパターンの適用(サイズ上限追加、タイムアウト追加、atomic ordering 強化、f64→固定小数点化、切り上げ除算化) | **Sonnet** | 本セッションの修正19件の大半がこのクラス。関数シグネチャと呼び出し規約を読めば機械的に正しく書ける作業で、上位モデルの追加コストに見合わない |
| 中規模機能の実装で複数ファイルに影響するが設計判断は少ないもの(FFmpeg エンコーダの実配線、WebGL2 描画パス接続、`release.yml` のマルチOSビルド化) | **Opus** | 実装手順は `ffmpeg_enc.rs` の TODO コメントや `docs/updater.md` に骨子が既にあり、複数ファイルの整合を保ちながら「指示書通りに組み立てる」作業。設計そのものより実装量が支配的 |
| セキュリティ設計判断・「実装するか止まるか」のスコープ判断・新規 unsafe を伴う実装(音声キャプチャ, PipeWire DMA-BUF, TOFU ゲート, ホスト側デフォルト変更の可否) | **Fable 5(または当時の最上位モデル)** | 本セッションで実例: (1) `PairingDialog` をそのまま流用すると PIN 未検証なのに検証しているように見える UX 欺瞞になると気づき `requirePin` 設計に変更した判断、(2) ホスト側 TOFU のデフォルトを変えると「破壊的変更」になると判断し環境変数opt-in に方針転換した判断、(3) `anyhow::Error::downcast_ref` が `.context()` でラップすると効かなくなる罠を事前に回避した設計。いずれも「動くコードを書く」以上の**判断の質**が結果を左右した |
| 広範なコードベース調査・監査(FEATURE_AUDIT 作成、商用ギャップ調査) | **Explore サブエージェント(委任) + 上位モデルで検証** | 委任自体は有効だが、本セッションで誤検知が1件出た実績があるため、サブエージェントの報告を鵜呑みにせず上位モデルが最重要項目だけ再検証する二段構成が必須 |

## skill の使い分け

| skill | 使うべき場面 | 本セッションでの実績/教訓 |
|-------|-------------|---------------------------|
| `code-review` | Rust の diff をコミット前にセルフレビューする | 本セッションでは未使用のままビルド未検証コミットを重ねた。**次回から Rust 変更のコミット前に必須化すべき** |
| `simplify` | 大きめの機能追加(TOFU ゲート等)の直後、重複/過剰実装を整理する | 未使用。TOFU ゲート実装後に一度通すべきだった |
| `verify` | UI 変更を実機(Tauri アプリ)で触って確認する | 未使用。`PairingDialog` の `requirePin` 分岐は `tsc` の型検証のみで、実際の描画・操作感は未確認のまま |
| `deep-research` | Web検索前提の外部調査(Qiita/Zenn/GitHub動向など) | **2回試行し2回とも週次検索枠切れで失敗**。現状は使えない前提で、Explore サブエージェント+コード実査に切り替えるのが正解 |
| `run` | Tauri アプリを実際に起動して動作確認する | 未使用。音声キャプチャ/HWエンコード実装(roadmap フェーズ1)では必須になる — ビルド可能な環境が前提 |
| `review`(PRレビュー) | GitHub PR が実際に作成された後のレビュー | 本セッションでは PR 未作成のため未使用。次にどこかで PR を出すフェーズがあれば使う |

## Agent(サブエージェント種別)の使い分け

| 用途 | 推奨 subagent_type | 本セッションでの実績 |
|------|---------------------|------------------------|
| 読み取り専用の調査(バグ探し、パス確認、機能監査) | `Explore` | 4回使用。`FEATURE_AUDIT.md` 作成・商用ギャップ調査・追加バグ探索のすべてでこれを使用し、実装は一切させなかった(ツール制限が Read/Grep 系のみで安全)。誤検知1件はこの型でも起きたので過信は禁物 |
| 大規模な多段階タスク(調査+実装を1エージェントに任せる) | `general-purpose` | 未使用。今後フェーズ1(音声キャプチャ等)で「実装してテストまで書く」を1エージェントに任せる場面があれば候補になるが、Rust ビルド不能な現環境では検証できないタスクを丸投げするのは危険 |
| 実装計画の設計レビュー | `Plan` | 直接呼び出しはしていないが、ハーネスの Plan Mode ワークフロー経由で類似の機能(理解→設計→レビュー→計画確定)を利用した |
| Claude Code/SDK 自体の使い方に関する質問 | `claude-code-guide` | 未使用(該当する質問が発生しなかった) |

**教訓**: 調査系タスクは `Explore` に一貫して委任し、コード変更(Edit/Write)は
メインループ側で行う分離が本セッションでは機能した。これは「サブエージェントの
出力を鵜呑みにしない」運用ルールとも一致する — 変更を自分の手元で行うことで、
コミット前に最終確認する機会を必ず確保できる。

## Loop / Workflow エンジニアリングの使い分け

| 仕組み | 使うべき場面 | 本セッションでの実績/教訓 |
|--------|-------------|---------------------------|
| `Workflow`(deep-research 等の多段オーケストレーション) | Web検索を伴う調査で、fan-out→検証→統合の構造が要る場合 | **2回試行し2回とも失敗**(週次検索枠切れ)。現状 Miru の作業には使えない前提を置き、コードベース内で完結する調査は `Explore` サブエージェント、外部動向調査は保留するのが正解 |
| `/loop`(定期的な繰り返し確認) | 「CIが通るまで監視」「PRレビューコメントに継続対応」など、終了条件が外部イベントに依存する反復作業 | 未使用。本セッションでは同一メッセージ(「このプロダクトの長所短所…」等)が**6回連続**でほぼ無変更のまま送られてくる場面が複数回あった。もしこれが「分析を定期的にやり直してほしい」という意図だったなら、手動でのメッセージ再送ではなく `/loop` + `ScheduleWakeup` を使うべきだった。逆に、本セッションの各分析は一回性の判断作業(ソクラテス式問答、機能監査)だったため、`/loop` 化はむしろ不適切 — **反復のたびに新しい情報が加わらないなら `/loop` 化しても無意味**、という判断基準を持つこと |
| 単発の `Agent` 呼び出し(このガイドの前セクション) | 上記いずれにも該当しない、独立した一回限りの調査・小タスク | 本セッションの主力。最も多用し、最も安定して機能した |

**教訓**: 「同じ依頼が何度も来る」こと自体は `/loop` を使うべきサインだが、
依頼内容が毎回同一で新情報が無い場合は、単に自動再送/クライアント不具合を
疑うべきであり、実際に本セッションでもその可能性を都度ユーザーに確認した。
`/loop` は「終了条件が外部イベント(CI結果、PRコメント等)に依存する」ケースに
限定して使うのが正しい判断基準。

## roadmap フェーズ別の推奨モデル(要約)

`docs/roadmap.md` セクション0.5 のフェーズに対応:

- **フェーズ0(ドキュメント是正)**: Haiku〜Sonnet で十分(実施済み)
- **フェーズ1(音声キャプチャ/HWエンコード/WebGL2/Wayland/CI/TOFU検証)**: 音声・
  Wayland の新規 unsafe 実装は **Fable5**、HWエンコード配線・WebGL2接続は
  **Opus**、CI検証やビルド確認自体は **Sonnet**
- **フェーズ2(配布パイプライン: 署名・自動更新)**: コード署名の実務(証明書取得
  フロー設計、`signtool`/`notarytool` 統合)は **Fable5**(セキュリティ+運用判断)、
  ワークフロー YAML の機械的な拡張は **Sonnet**
- **フェーズ3(運用品質: crash reporter/アクセシビリティ)**: 設計(何を収集し何を
  収集しないかのプライバシー判断)は **Fable5**、`aria-*` 属性の機械的な付与は
  **Sonnet**
- **フェーズ4(スコープ最終整理)**: 製品判断そのものなので **Fable5 + 人間確認**

## 運用ルール

1. **どのモデルで書いた Rust 変更も、コミット前に `cargo test --workspace`
   相当のビルド検証を必須とする**。本セッションはサンドボックス制約で12件以上
   ビルド未検証のままコミットした — この状態を常態化させてはならない。
2. **調査結果は鵜呑みにしない**。サブエージェントの指摘した「バグ」は、
   直接コードを開いて自分で再確認してから対応する(本セッションで誤検知1件を
   確認済み)。
3. **セキュリティ関連の diff(認証・暗号・信頼判定)は Fable5 級のモデルか
   人間のレビューを必ず経る**。Sonnet/Opus 側の機械的パターン適用の範囲を
   超えるため。
4. **フロントエンド変更は `npx tsc -b --noEmit` を必ず通してからコミットする**
   (Rust と異なりこの検証は現環境で実行可能)。
5. **調査は `Explore` サブエージェントに委任し、変更(Edit/Write)はメインループが
   自分で行う**。委任と実行を分離することで、コミット前の最終確認機会を失わない。
6. **`Workflow`(deep-research)は現状使えない前提を置く**(週次検索枠切れの実績
   2回)。`/loop` は終了条件が外部イベントに依存する反復作業にのみ使い、
   毎回同一内容の一回性判断作業には使わない。
