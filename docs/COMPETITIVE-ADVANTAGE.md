# Competitive Advantage — Miru (2026-11-22)

方法: 競争優位性プログラム。競合調査（有料・無料を問わず）→ お金の流れの
分解 → マスク思考法＋ソクラテス問答を、意味のある知見が出るまで反復
（2ラウンド実施）。判定の出発点は作成者の原則: 個人データを持たない／
提供はソフトウェアのみ（運営費を負担しない）／本体は無料。
既存の docs/competitive-analysis.md（機能マトリクス、本書はその続編）。

お金が溜まる先は3つ: (a) 席課金（誰が・何台を・同時に何接続かという
メーター）、(b) モデルのトークン課金（画面を見るたびに課金され、
コストはステップ数の二乗で伸びる）、(c) 管理と証跡（RustDesk Pro が
示す通り、セルフホスト勢でも金になるのは監査ログ・SSO・管理画面）。
そして「権限の発行・失効・検証可能な監査」という層そのものは、
(a) はアカウント/クラウドと一体でしか売らず、(b) は中立性と責任回避の
ために意図的に持たない。商品として不在の層になっている。

## 反復の記録

### ラウンド1 — 「リモートデスクトップ製品である」を疑う

- 削除テスト: 画面転送・コーデック・キャプチャを全部消しても、
  capability トークン＋監査ログ＋MCP の「AI に PC を触らせるための
  権限・証跡層」は単独で製品として残る。
- 逆にその層を消すと、残るのは RustDesk より遅く（LAN 遅延は目標値で
  未測定）、AV1 HW・モバイル/Web クライアントが計画段階の
  リモートデスクトップで、存在理由が消える。
- 結論: 製品の本体はリモートデスクトップではなくエージェント制御の
  信頼層であり、画面転送はその最初の利用例だった。

### ラウンド2 — 「頭脳（モデル）が価値の源泉」を疑う（前提が崩れた）

- モデルのお金はトークン課金に流れ、モデルベンダーは computer use を
  「実行は利用者側・安全層は実装者責任」と設計している。ベンダーは
  権限管理を持てないのではなく、持たない構造的理由がある（特定の
  実行環境に踏み込むと中立性と責任範囲が壊れる）。
- 消えたもの: モデル内製、独自クラウド、公式リレーの運営。
- 生き残ったもの: どのモデルでも差せる中立の権限・証跡層
  （MCP という標準プロトコルの上に立つ）。
- 競合は TeamViewer でも将来の公式モデル機能でもなく、この層は
  市場に不在である、というのが崩れた前提の先にあった知見。

## 構造的優位

Miru は、AI エージェントに実機を触らせるための権限（capability）と
証跡（改ざん検知監査）を、モデルにもクラウドにも依存しない単一の
OSS 層として提供する。リモートデスクトップ勢は席課金のために
アカウントとクラウドを手放せず、モデル勢は中立性と責任回避のために
実行側の権限管理を持たないため、この層は両者の収益構造の外側に
あり、運営サーバーを持たない Miru だけが無条件に無料で出し続けられる。

補強する既存の実態:

- capability トークンは Ed25519 署名・TTL ≤15分（hard cap）・
  capability 単位の rate limit と日次上限・revocation list による
  即時失効（panic rotation）を持つ。
- 監査ログは hash-chain で改ざん検知可能、redaction は append 経由で
  強制されバイパス経路が無い。`miru-host audit verify` でオフライン
  検証できる。
- 公式シグナルサーバーは存在せず、作成者は利用者のデータを
  一切持たない（PRIVACY.md）。MCP は標準プロトコルで、モデルの
  乗り換えに層ごと捨てる必要がない。

## 残りの機会（順位つき）

1. README の看板を「権限と証跡の層」に寄せる（本書と同梱で実施）。
   現行は「リモートデスクトップ＋AI エージェント基盤」の対等な
   二枚看板で、本体が埋もれている。
2. 「モデルを差し替えても同じ権限・監査が効く」ことの実証を
   初回成功の形にする: Claude 以外の MCP クライアント（Cursor /
   Codex は allowlist 実装済み）での接続手順を README から
   辿れるようにする。中立性は実証されて初めて優位になる。
3. 監査の検証可能性を入口に変える: `miru-host audit verify` の
   実行例（正常時と改ざん検知時の出力）を README に載せ、
   「信頼してください」ではなく「確かめられます」を最初の
   成功体験にする（TRUST.md の方針と一致）。
4. CI の有効化は .github/workflows-proposed/ に提案済みで、
   判断待ちの状態が続いている。有効化されれば「252 passing」の
   実測値が継続的に裏づけられ、看板の信頼性が上がる。
5. リモートデスクトップとしての性能競争（遅延・AV1 HW）は
   最後に回す。信頼層の看板が立たないうちは、Parsec / RustDesk と
   同じ土俵の消耗戦になる。
